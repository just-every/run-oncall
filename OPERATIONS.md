# Operating Oncall

README.md opens with the root command sequence. `describe` is authoritative for parser flags; `check` is structural, not a hosted health proof. `rer` provides the pinned Node and pnpm. SQLite/D1 is the relational store; .wrangler/state is canonical local data, .dev.vars contains private settings, .rer/local is local key custody. Never commit these.

The protected API retains held password accounts and adds Base email/dev identity for new installations. On local and hosted apps, the configured owner uses native email links when mail is enabled or guarded `rer signin` when mail is explicitly off. Members created by an administrator use their installation-local workspace name and password at `/signin/local`; Oncall sends no invitations. Anonymous first-admin bootstrap at `/api/setup` remains loopback-only. All private HTTP mutations require same-origin requests and current member/session authority. Ingress credentials are scoped to services and grant no private read access. /setup and /signin use Base native handlers; no private Start function exists.

Export/import use Base portability for the supported entire installation, including move-in records and journal. Base sessions, Oncall sessions and dev credentials are excluded; imported pending historical timers must remain paused and cannot resume because delivery is OFF. Restore requires an empty destination; use the separate protected checkpoint API for explicitly reviewed replacement. Retained third-party originals may contain personal data: keep archives private.

Release 1 hosts incident coordination alongside the team's existing pager, with paging OFF and no independent standby prerequisite (owner direction, 16 October 2026). Release 2 paging and independent standby are not built. Keep existing pager routes and notification settings authoritative; hosted coordination does not add delivery channels, dual intake, configuration synchronization or external role-move announcements.

Use the published `rer` pin in package.json. Prepare the owner with a real mailbox using `"$HOME/.local/bin/rer" setup --owner-email you@example.com`. `"$HOME/.local/bin/rer" deploy --environment production --dry-run --non-interactive` builds and validates a local plan without credentials or Cloudflare requests and changes nothing remotely. It creates no deployment record and checks neither target secrets nor deployment permissions, remote readiness or mail delivery. For `rer deploy`, supply `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN` privately for the intended account. Mail is optional. With email off, set `MAIL_PROVIDER=none` and leave sending inputs unset. The owner runs `"$HOME/.local/bin/rer" signin` from the deploying checkout with its Cloudflare credentials and recorded deployment. Open the private URL printed on its own line. For emailed sign-in links, set `MAIL_PROVIDER=sendgrid`, `SENDGRID_API_KEY` (or `MAIL_API_KEY`) and a verified `MAIL_FROM`. Choose the mail setting explicitly. The command deploys the app and D1 migrations, checks the deployed identity, automatically claims the configured owner and retires the one-time setup token. With email enabled, the owner can also request a sign-in link at the HTTPS app address. See [Install and run](docs/install.md#host-for-your-team).

The maintained managed-installation journey in `tests/transfer.mjs` runs the production dry run after dev and preview exit, removes Cloudflare and mail credentials from the child environment, and checks local-only completion, no deployment record, clean production artifacts and byte-identical private settings restoration. It also invokes `rer build` after removing prepared output before checking production preview. These observations establish local command behavior; R-1 remains dated prior field evidence.

Hosted D1 and local `.wrangler/state` are separate stores. Deploy does not upload local records; the maintained export/import commands target local state. Redeploy with the same deployment record and Cloudflare credentials to retain the hosted owner and records. Keep the private `.rer/deploy/` deployment record: removal uses it to identify only the resources this installation created. `"$HOME/.local/bin/rer" deploy --remove --yes` uses the same credentials, deletes recorded resources and reads each back as absent. It keeps your local checkout and data. A dry run, local test or structural check is not evidence of remote removal or mail delivery.

D1 reads stay flat as history grows. Each Worker isolate keeps a copy of the workspace and paging rows and catches up from `oc_read_changes`, a change log the database's own triggers write for every change to those rows, so an unchanged console poll reads a few rows and a changed one reads only what changed. A new isolate starts from `oc_read_snapshot`, which the minute cron rewrites when it falls 256 changes behind. A portable import, a point-in-time restore or a gap in the log makes the next read load every row once. `tests/read-budget.mjs` holds console polls, the minute cron with and without a due on-call sweep, and cold reads well under one full read with 30 days of history at 40 alerts a day.

If coordination is unavailable, continue through the existing pager and your team's incident communication process. No recovery or standby delivery guarantee is made. Paging acceptance belongs to a later release with independent standby, real-phone and provider-failure drills.
