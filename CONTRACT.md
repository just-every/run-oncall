# Oncall product contract

Target edition · 16 October 2026 · US-first · USD.

Oncall owns the full on-call alerting and incident-response job: receive monitoring or phone-in incidents, identify coverage, wake a responder through real phone/SMS/push, escalate until acknowledged, coordinate verified recovery, communicate and finish the follow-up. The first buyer is a US software/IT operations team replacing PagerDuty, Opsgenie / Jira Service Management incident response, or Splunk On-Call (VictorOps). The target also competes with incident.io On-call, Rootly and Resolve AI through integrated response and bounded agent work. This is a destination contract, not a description of what currently ships.

The approved 16 October scope governs these clauses. Release 1 remains hosted coordination beside the existing pager, with production paging OFF. Writing a target does not activate providers, change the approved UI/homepage or waive the independent standby and real-phone cutover requirements. Existing IDs remain stable. Clauses OC-001–022 retain release guarantees; OC-023 onward completes the purchased job. A clause is **done** only within its stated limits and cited exercising flow; **partial** names the implemented subset; **missing** has no implementing flow. Acceptance evidence is the public journey required to complete the clause; merely listing it is not a passing run.

The OC-003 and OC-006 policies below authorize scoped machine coordination and explicitly approved signed response events under OC-053, while preserving human-session authority and paging OFF.

## Preserved coordination guarantees

- **OC-001 — Event identity and alerts.** Persist accepted events separately from alerts and human incidents. Repeated source event IDs return the original receipt; changed bytes with the same identity conflict. A deduplication key groups active alerts only within its source/service/environment; recovery affects the matching alert and never resolves an incident.

  **Acceptance evidence:** POST signed and bearer events through /api/ingress/:source; repeat a normalized identity, conflict changed content, send recovery before trigger and after a newer generation, and inspect protected state. Verify grouping across multiple sources without merging service/environment boundaries.

  **Status:** partial

- **OC-002 — Routing replay.** Retain routing policy version and explanation at admission. Replay is read-only, returns ordered decisions, and produces no alert, incident or external effect. Unmatched signals remain visible and unowned; suppression reasons remain inspectable.

  **Acceptance evidence:** Admit a severity-routed event, change policy, POST /api/replay and compare the immutable admission explanation with the proposed decision in submitted order; compare state before/after for zero writes.

- **OC-003 — Roles and authority.** Incident changes require an active authorized human session or an explicitly scoped OC-053 service-account capability. A machine is attributed as a service account and never gains human-session, member-management or human-review authority. Viewer reads; responder coordinates; admin manages services/policies/members/import. Ingest credentials grant no read or human authority. Bearer and signed intake return only `duplicate`, stored event `id`, source `eventId`, `service`, `observedAt` and `acceptedAt` (201 accepted; 200 deduplicated). Routing decisions, snapshots and alert identities stay behind authorized read/export doors; scoped OC-053 reads disclose only granted service records, and archive/export authority remains session-protected. Revocation takes effect on the next request. Every mutation enforces current authority server-side. The stakeholder role that reads only business-service status and approved updates is specified and tracked in OC-061.

  **Acceptance evidence:** Use anonymous, expired, revoked, viewer, responder and admin sessions on reads, commands, sources and archives; revoke or downgrade while a real HTTP mutation is incomplete and prove no publication. Verify minimal intake receipts disclose no private routing data.

- **OC-004 — Incident state transitions.** Incident state transitions are explicit. Acknowledgment assigns responsibility. Resolution requires recovery evidence and a summary, independently of alert recovery. Optimistic revision checks reject stale edits. All accepted changes append an attributed timeline transactionally with state. This resolution rule governs declared incidents; an alert-only page that its source recovers closes without a human summary under OC-056.

  **Acceptance evidence:** Declare from admitted alerts, acknowledge, reject stale concurrent changes, clear the source alert, refuse resolution without evidence and summary, then resolve and inspect the attributed timeline over HTTP.

- **OC-005 — Copied runbooks.** Runbooks are copied into the incident at declaration; future service edits never silently rewrite incident instructions. Follow-ups carry owner, due date, open/completed state and completion evidence. Resolved incidents retain open work and editable review.

  **Acceptance evidence:** Declare an incident, edit its service runbook and confirm the copied incident steps remain unchanged; create an owned due-dated action, require completion evidence and retain unfinished work and review after resolution.

- **OC-006 — Bounded outbound incident effects.** Only signed OC-053 response events to an endpoint a current administrator explicitly approved may leave the incident workspace in release 1. No paging provider notification, AI call, production action or Lamp publication occurs in release 1. Configured remote mail sends sign-in links only. Handoffs are minimum summaries with stable identity and visibility; exported draft is explicitly unreviewed. Source links grant no access. External acceptance/delivery/acknowledgment are distinct later records.

  **Acceptance evidence:** Use coordination and handoff preparation/export on a normal installation with no approved OC-053 endpoint; prove no paging receipt, production action, AI call or external publication occurs. Confirm draft exports remain unreviewed and source links confer no access. Approved OC-053 events are proved under OC-053.

- **OC-007 — Native archive.** Native archive preserves services, policies, incident/alert/event/timeline identity and attribution, runbook and follow-up history. Validate schema and references before atomic restore. Invalid restore preserves existing data. Do not export authentication secrets/sessions. Released migrations remain immutable; verify prior-data transitions.

  **Acceptance evidence:** Export through /api/archive; restore valid held records and reject malformed references/storage failures without losing prior data. Inspect event, incident, runbook, action, timeline and attribution identity and confirm authentication material is absent.

- **OC-008 — User-authored records kept.** No automatic deletion of user-authored incident records. Owner export/restore is supported. Ingress accepts bounded structured fields. Provider and incumbent-compatible intake retain bounded structured evidence and no raw bodies under OC-059. Incumbent-compatible endpoints and provider adapters use the larger per-provider bounds of OC-059. No arbitrary remote fetching or runbook execution. Display user content as text, never HTML.

## Admission and authority refinements after independent review

The public intake request keys, authentication modes, field limits, service-ID lookup and a curl example are documented in [Incidents and alerts](docs/incidents.md#send-an-alert-event).

Identity is source + eventId; conflicts compare the normalized allowlisted signal fields (canonical timestamps and trimmed strings), rather than irrelevant JSON whitespace/order or discarded fields. Receipts, admission order, decision snapshot and alert mutation commit atomically. Each signed/bearer source is explicitly scoped to service identities; the service binds its environment. A routed key (OC-072) selects exactly one service in its allowed scope for each event before identity, deduplication and generation apply. On the native Events API, lifecycle generation is required: trigger and recovery must carry the same generation. Incumbent-compatible endpoints whose payloads carry no generation (OC-055) never require one: Oncall derives it from the source's deduplication key and receipt order, as OC-055 specifies, and the same tombstone and reopening rules then apply. Recovery before trigger creates a recovered tombstone; later trigger for that generation records evidence without reopening. Reopening needs a new generation. A delayed recovery can only close its own generation, never a new alert.

Stage 1 routes coordination ownership, with no timed escalation or paging. Replay returns historical decision/ownership/policy/evaluation snapshot beside the proposed current decision in submitted order; it does not claim schedule replay. All active members see all workspace incident data. Admin/responder/viewer permissions differ from incident commander attribution. Any active responder/admin can attest recovery and follow-up evidence; attestation is a human claim, not automatic measurement verification. Archive and restore require current admin authority; handoffs remain internal. Restore replaces application state while preserving the current administrator identity; credentials remain installation-local, other sessions are revoked, clients reload state. Historical and inactive identities are retained.

### Scoped machine and response-event policies

- **OC-003 / OC-006 policy (21 October 2026, deliberate requirement change; authorized by the OC-053 fleet brief):** The former session-only incident-change requirement now also admits explicit, service-scoped machine capabilities through `/api/v1`. Formerly, routing decisions, snapshots and alert identities were readable only through session-protected doors. A token with the matching read permission now reads its granted services' records, including the incident alert IDs those records carry through the services, schedules, incidents, actions, analytics and integrations families; intake routing-decision records and frozen intake snapshots remain session-only. It has no archive, export or audit door. A `services:write` token may update granted service definitions, which is an administrator action for humans, but cannot create services or widen its grant. The former prohibition on external incident publication now permits only administrator-approved minimal signed response events through the OC-053 outbox. Existing human role checks, human-review acceptance, protected archive/export, minimum intake receipts and paging OFF remain required. Token authority is never inferred to be a human response. A machine acknowledgment must name an active responder, who becomes the incident's commander and assignee. The timeline and audit record it as the service account's act naming that member, never as that member's own acknowledgment. A token cannot accept human-review follow-ups. Completion it supplies under the evidence policy is an automation claim, not a human attestation. Delivery is receiver acceptance, not acknowledgment by a person.
- **Security consequences:** Machine keys grant only named API permissions and services; they cannot create sessions or manage members. A key or endpoint acts only while the administrator who created it remains an active administrator. Demotion or removal suspends it from the next request and at dispatch, and its authority never transfers. Endpoint approval declares exact recipients and minimal data fields; installation-local digest/AES-GCM custody, dispatch-time authorization, credential-revision fences, bounded attempts, signed receipts and protected replay apply. Revocation cannot retract bytes already sent; ambiguous outcomes remain uncertain. Restore transfers history without tokens, signing keys, approvals or automatic sends. Erasure severs matching automation labels and local capabilities without rewriting permanent pseudonymous audit facts. Each event body is exactly `operationId`, `type`, `service`, `incident`, `revision`, `state` and `at`, frozen at the domain commit. It carries no names, summaries, notes, evidence URLs or contacts. It is signed with HMAC-SHA256 hex over `timestamp + "." + body`, using a per-endpoint key that is never returned, logged, exported or written to audit. Only an authenticated receiver receipt records `sent`, and an unsigned success is `uncertain`. Recipients are literal globally routable IPv4 HTTPS addresses on port 443, with no hostname, DNS lookup, userinfo, query or fragment. Redirects are never followed. An operation gets at most five attempts. Service-account keys, held as SHA-256 digests, never enter audit or logs. Creating, rotating, revoking and replaying are administrator-only and each commits with its OC-041 audit entry.
- **Evidence and gaps:** `tests/runtime.mjs` extends the emitted HTTP journey with `tests/automation.mjs`; `tests/transfer.mjs` and `tests/checkpoint-cli.mjs` exercise populated inactive transfer and erasure; `tests/automation-browser.mjs` exercises the existing settings pattern at 1440 and 390. `tests/automation.mjs` (creator demotion/removal) exercises next-request read/write refusal, separate origin/endpoint/receiver dispatch custody, no transfer to another administrator and refusal after restart; its machine acknowledgment asserts commander/assignee and service-account timeline/audit attribution. - **OC-071 — Notification bundling and per-message reply mapping.** Personal notifications are composed per responder and channel, not per obligation. **Bundling:** when an attempt falls due for a responder on a channel, Oncall waits at most 5 seconds (the bundling window) and sends one notification carrying every attempt due to that responder on that channel in that window. - **OC-072 — Routed intake keys that pick the service per event.** Beside the service-scoped key, Oncall offers a **routed integration key**, created at workspace level or team level. Each routed key has an **allowed scope**: the explicit set of services it may route to. A team-level key's scope can hold only that team's services. A routed key is accepted wherever a service key is: on every OC-055 endpoint (PagerDuty Events v2 `routing_key` and v1 `service_key`, Opsgenie Alert API `GenieKey`, and Splunk On-Call REST, whose URL routing key becomes a matchable field), on the OC-030/031 adapters, on OC-033 webhooks and on the native Events API. Authentication, revocation, rotation, rate limits and minimal receipts are the same as for a service key, and so are the incumbent-shaped responses. Each service key and each routed key has its own rate allowance, owned by the key's record and not by its secret: rotating a key neither resets nor doubles it, and revoking it ends it. Two things are counted per key over a rolling one-minute window. (1) Requests: every authenticated request, including duplicates and rejected payloads, default 600 per minute. (2) Newly admitted events: an event that creates a new receipt counts once, a repeat of an already-admitted event and a further alert grouped into an existing group count zero, default 120 per minute. An owner or admin may set lower or higher values per key within a documented ceiling. A request over either allowance gets HTTP 429 with a Retry-After computed from when the allowance actually frees, and nothing is silently dropped: the sender is told, and the owner is notified once per window, with the key name and count, that a key was throttled. The allowance recovers after the actual window, not on a reset timer. Email intake keeps its separate 60 new receipts per minute per address, and a throttle refusal happens before grouping so it never changes grouped-alert custody. The 10,000-receipt capacity stays a separate storage bound. The 10,000-receipt count is a local limit; it becomes a hosted capacity only under OC-073. An atomic batch whose new-event count exceeds the key's configured allowance is refused whole with 429, a machine-readable batch_exceeds_allowance code, the batch count, the key's allowance and an instruction to split the request or raise the allowance, without Retry-After because it can never fit unchanged. Ordinary temporary throttles retain actual-expiry Retry-After. No grouped custody is partially mutated; the owner is still notified once per window with the key name and count. **Routing rules:** each routed key has one versioned, ordered rule set of up to 100 rules, and the first matching rule picks exactly one service. A condition is equals, contains, exists, or a regex match or non-match on the linear-time engine of OC-070, and conditions combine with all or any. Conditions read the transformed event (summary, source, severity, component, group, class, urgency) and the raw payload by path. The paths include PagerDuty `payload.source`, `payload.component`, `payload.group`, `payload.class` and `payload.custom_details.*`; Alertmanager `labels.*`, `annotations.*`, `commonLabels.*` and `groupLabels.*`; Datadog `tags` as key:value pairs; Opsgenie `responders`, `teams`, `tags`, `details.*`, `entity` and `source`; and the Splunk On-Call routing key, `entity_id` and custom fields. **Dynamic routing:** a rule can take a service name or ID from a chosen field, optionally through a regex capture group. The value resolves only within the key's allowed scope. A value that names an unknown service, or one outside the scope, never routes there: the event goes to the catch-all, with the diagnostic "dynamic route target outside key scope" naming the field and value. A rule that names a fixed service outside the scope is refused when it is saved. **Catch-all:** every routed key states its catch-all, and an event is never silently dropped. The catch-all is either (a) **record unrouted**, the default as in PagerDuty: the event is retained as a suppressed, unrouted alert that never pages, shown in the integration owner's unrouted queue with the rules evaluated and counted on the key's health; or (b) **route to a named service** in the scope. A catch-all change applies to later events only. An integration owner can re-admit a retained unrouted event to a chosen in-scope service as a new, attributed admission that keeps the original receipt. **Per-service identity:** the service is chosen first. OC-001 identity, the OC-055 derived generation, OC-043 service orchestration and OC-057 urgency then apply within that service. The same `dedup_key`, alias or `entity_id` routed to two services opens two separate generations that never merge. Acknowledge, resolve and close events pass through the same rule set and act only on the generation open for that key on the service they route to. If they route to a service with no open generation for that key, the result is a no-effect receipt naming the routed service, and the integration owner sees a "resolve matched no open generation" diagnostic that lists the services where that key is open. **Explanation and replay:** every receipt and every OC-002 explanation names the routed key, the rule-set version, the matched rule ID (or "catch-all", or "dynamic" with its field and value) and the chosen service. A draft rule set replays against retained events chosen by time range or ID (up to 10,000 events). Replay returns each event's ordered decision, a diff against the published version, and a warning for every open generation whose later resolve would route to a different service. It makes zero writes. Publishing a version is attributed and audited, and it is refused when the draft's base version is stale. **Bounds:** the OC-059 request bounds apply to routed keys. When an over-limit or partly unreadable request authenticates only to a routed key, each readable alert is routed by the rules. The incomplete-intake alert for the unread remainder goes to the catch-all service and pages it under that service's policy. When the catch-all is record unrouted, the alert is held in the unrouted queue and pages the key's integration owner as a user-targeted high-urgency page under OC-068. The response is 202 with the truncation flag. **Management and migration:** routed keys and rule sets are managed in the UI, the OC-053 API and Terraform (OC-062).
