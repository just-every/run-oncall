# Connect an existing alert sender

Oncall accepts PagerDuty Events v1/v2, Opsgenie Alert API and Splunk On-Call REST requests for incident coordination. **Keep your existing pager active. Oncall paging stays OFF.** Accepted input records an alert; it does not call, text, push, start escalation or notify an integration owner.

In **Alerts & events → Compatible alert intake**, create a service-bound integration, generate a private key and save it in the monitor's secret settings. Keys admit events only; they cannot read the workspace or acknowledge a human incident. Choose a distinct key for every integration. The provider and service binding cannot change after creation. An administrator can rotate or revoke the key with an immediate effect on subsequent admission; conflicting in-flight writes refuse without confirming acceptance.

## Receiver addresses

Use your installation's app origin with these paths:

| Sender | Path | Credential | Success |
| --- | --- | --- | --- |
| PagerDuty Events v2 | `/v2/enqueue` | `routing_key` in JSON | 202 with `status`, `message`, `dedup_key` |
| PagerDuty Events v1 | `/generic/2010-04-15/create_event.json` | `service_key` in JSON | 200 with `status`, `message`, `incident_key` |
| Opsgenie create | `/v2/alerts` | `Authorization: GenieKey KEY` | 202 with `requestId` |
| Opsgenie action | `/v2/alerts/ALIAS/close?identifierType=alias`, `/acknowledge?identifierType=alias`, `/notes?identifierType=alias` | Same header; URL-encode the alias | 202 with `requestId` |
| Opsgenie request status | `/v2/alerts/requests/REQUEST_ID` | Same header and integration | 200 with committed request outcome |
| Splunk On-Call | `/integrations/generic/20131114/alert/ENDPOINT_KEY/ROUTING_KEY` | Endpoint key in URL; routing key is a label, not authentication | 200 with `result`, `entity_id` |

PagerDuty v2 accepts `trigger`, `acknowledge` and `resolve`. A trigger supplies `payload.summary`, `payload.source` and severity; acknowledge/resolve need no payload. PagerDuty v1 uses `event_type`, `incident_key` and `description`. Images are retained only as safe HTTP(S) links and are never fetched.

Opsgenie create accepts `alias`, `message`, P1–P5 `priority`, `tags` and `details`. Notes supply `note`; close and acknowledge accept empty objects. Missing priority uses Opsgenie's P3 default; an unknown priority maps to critical/P1. P4/P5 map to warning/info. This is intake severity mapping; timed urgency and notification rules are not implemented.

Splunk accepts `CRITICAL`, `WARNING`, `INFO`, `ACKNOWLEDGEMENT` and `RECOVERY` with `entity_id`. INFO adds context to an open generation and never opens an alert. Only CRITICAL/WARNING open one. The endpoint credential may appear in sender/proxy URL logs; configure those systems to redact that URL segment.

For an Alertmanager `pagerduty_configs` receiver, change its `url` to the corresponding v1/v2 address and use this integration's key in `service_key` or `routing_key`. A Datadog webhook already producing a PagerDuty v2 body can change its URL and configured key. Products whose built-in destinations hard-code the incumbent host need their generic webhook configuration. An administrator may now supply a service-bound incumbent integration key separately after the keyless file import, then explicitly activate it. Complete account migration and routed-key imports remain unbuilt. Native Oncall keys keep the existing 32–200 character profile.

## Lifecycle and retained context

The integration, service/environment and deduplication key identify an outage. A trigger opens a generation if none is open; repeated triggers append observations to that same generation. Recovery closes the generation open when it is admitted. A later trigger, including an identical body, opens a new generation. Recovery with none open remains a **no-effect** receipt and cannot suppress a later trigger. Missing trigger keys receive a generated identity returned to the sender; each unkeyed trigger opens separately.

A source acknowledgment is attributed to the integration in its durable receipt. It never acknowledges, resolves or verifies recovery of a human incident. There is no escalation to stop in this coordination release. Source recovery also leaves a declared incident open for a responder's evidence-backed resolution.

These compatible protocols provide an outage key rather than a unique delivery identity. Admission order is authoritative: without a sender-provided cycle, a delayed recovery cannot be distinguished from a fresh recovery of the current generation. Native `/api/ingress/:source` retains its explicit event/generation semantics. PagerDuty v1 `incident_key` and v2 `dedup_key` allow 255 characters; Opsgenie `alias` allows 512. Splunk `entity_id` retains the conservative local 200-character bound (the linked provider page does not state a maximum). Over-limit or malformed identities and invalid explicit actions receive the incumbent refusal envelope and retain no alert or incomplete-intake receipt; identities are never truncated or merged. Missing or unreadable fields still use OC-059 incomplete custody. Identifiers cannot begin/end with whitespace or contain ASCII controls, DEL or unpaired Unicode surrogates. Limits are measured in UTF-16 code units; this character profile is an explicit conservative assumption, unverified against live senders.

Every admission has a protected receipt with source, service, action, generation, outcome, reported time (or a missing-time indication), bounded context. Trigger and effective-recovery receipts link to native events with retained routing decisions. Context is at most 8 KiB, nested fields and lists are bounded, credential-like fields are redacted, and omitted/overlong fields carry a truncation indication. No raw body is retained. Links grant no access and are never fetched. The UI shows source acknowledgment, no-effect actions and recovered generations separately.

Requests are parsed within a 512 KiB bound. Authenticated oversized or partly readable compatible input retains bounded structured evidence and complete readable alerts, with high-urgency incomplete custody and a recorded owner notice under OC-059; it returns 202 with a truncation flag and stores no raw body. Routed keys apply their published catch-all. Paging and external owner delivery remain unbuilt; paging stays OFF.

PagerDuty v1 and v2 refusals keep the incumbent error envelope (`status: "invalid event"`). A rolling-minute request or event allowance refusal is HTTP 429 with a Retry-After computed from when that key's usage actually expires. The installation's 10,000-receipt capacity refusal is also 429, with no Retry-After because no timed window frees it: export before extending capacity. A PagerDuty request carries one event, so the intrinsic over-allowance batch refusal (`batch_exceeds_allowance`, without Retry-After) applies only to the batch-capable monitoring receivers; see [per-key allowances](routed-intake.md#per-key-allowances). Concurrent admission changes return 503 so the sender can retry. Authentication, authorization and other invalid-event errors, including an unknown key, return 400 in the same envelope. Never treat a refusal as accepted. The 10,000-receipt count is a local limit; it becomes a hosted capacity only under OC-073.

## Custody and acceptance

Native/checkpoint and portable archives retain integration definitions, lifecycle history and receipts. Verification hashes stay installation-local and are excluded. Restore removes keys and marks all integrations inactive; reconfigure each key before intake can resume. Restoring history never replays effects.

The public Worker journey exercises request/response formats, scope, concurrent admission, failure rollback, restart and inactive restore. Local receiver checks do not prove an external provider sent a real monitor notification. Provider accounts, live send/fire/recover acceptance, routed-key imports and production paging remain unproven. Local synthetic tests cover administrator-supplied incumbent key custody and the stated identity limits.

Protocol references: [PagerDuty v2](https://docs.pagerduty.com/developer/send-alert-event), [PagerDuty v1](https://docs.pagerduty.com/developer/send-v1-event), [Opsgenie Alert API](https://docs.opsgenie.com/docs/alert-api), [Splunk REST](https://help.splunk.com/en/splunk-cloud-platform/alert-and-respond/splunk-on-call/integrations-with-splunk-on-call/rest-endpoint-integration-for-splunk-on-call), [Alertmanager configuration](https://prometheus.io/docs/alerting/latest/configuration/).


## Administrator-supplied incumbent keys

Saved files still refuse every credential-bearing field. After a completed keyless integration import, an administrator binds the supported integration to one existing service, supplies its incumbent credential once in a password field, then separately chooses **Activate compatible intake · paging OFF**. Supply and rotation always leave the integration inactive. PagerDuty v1/v2, Opsgenie API integrations and Splunk REST endpoints are supported; other integration kinds stay inactive with a named limitation. Native Oncall key rotation remains available through the existing integration management door.

Only SHA-256 verification hashes are stored. The supplied key never comes back in a response, document, audit, archive or checkpoint. Activation creates a new native Oncall key shown once; dismiss it after storing it privately. Both credentials identify the same source and outage generation. Revocation deletes both hashes immediately. Restoring a checkpoint or portable archive keeps the source inactive and keyless; it needs a fresh supply and activation. Key custody marks the imported object edited, so import undo refuses to overwrite it.

PagerDuty incumbent keys use the documented 32 hexadecimal characters. Opsgenie and Splunk incumbent credentials use a conservative 32–200 printable ASCII character profile without whitespace, **unverified** against every account's key format. For Splunk, supply the REST **endpoint credential**, not the URL routing label: the latter remains non-secret routing context and grants no authentication. That label has a conservative local 200-character bound and the same identity character rules, **unverified** as a provider maximum. Sender/proxy URL logs still need the endpoint segment redacted; Oncall does not fetch or validate the key with a provider.

The linked PagerDuty references confirm 255-character identities and 1,024-character summaries/descriptions; the linked Opsgenie reference confirms 512-character aliases and 130-character messages (checked 23 October 2026). Context retains Oncall's existing bounded/truncated treatment, including its 300-character title; these provider text limits are not a claim of full sender equivalence. Live sender acceptance remains dated owner-role work, not performed here. Paging stays OFF.

## Integration email

In **Alerts & events → Integration email**, an administrator creates an address bound to one service, its environment and an active integration administrator. Email is **off by default**: configure the optional `INBOUND_EMAIL_DOMAIN` binding (for example `alerts.example.com`) in the installation. For `rer deploy`, supply it as an environment input or in the private `--env-file`; the optional binding is declared in `deploy.json`. Locally set it in `.dev.vars` or the environment before `rer dev`. No domain is inferred from the owner or the sender.

Generate and privately copy the whole email address **before saving**. This installation chooses the unguessable local part. The address is an intake credential, stored as a SHA-256 digest, never returned by reads, exported or echoed after saving. Rotation requires a fresh local part, immediately retires the old address and preserves its refused-delivery activity. Revocation stops admission. It grants no workspace read, sign-in or incident mutation authority.

At Cloudflare, enable **Email Routing** on the configured domain, then create an **Email Worker** routing rule: match the **literal To address** you copied and choose this installation's deployed Worker as the destination. Create the rule before sending and allow it to propagate: an API acknowledgement can precede SMTP readiness. Confirm a real delivery before enabling the monitor. An unrouted address can bounce and enter your sender provider's suppression list; once routing is ready, remove only that address's suppression before resending. Do not use an HTTP webhook to deliver email: only the Worker's `email()` handler accepts inbound delivery. See [Cloudflare's Email Workers handler](https://developers.cloudflare.com/email-service/api/route-emails/email-handler/). Email Routing and the Worker must belong to the installation's authorized account.

**The sender is not authority.** Cloudflare's first `Authentication-Results` must report an aligned DMARC pass for the header From domain; failed, missing or spoofed authentication is quarantined. Only that authenticated From value is available to sender conditions. A sender condition can select a rule but cannot grant account access. The integration address supplies the service scope. Unknown/revoked addresses, inactive owners, unmapped service/environment and malformed or over-limit messages are refused with fixed, secret-free diagnostics. Known addresses keep their activity; unknown addresses appear in the administrator's unassigned activity. No received links or attachments are fetched.

### Modes and rules

Each address publishes immutable numbered versions of one mode:

- **Subject deduplication** (default): trim the subject, collapse whitespace and remove repeated leading `Re:`, `Fwd:` or `FW:` markers. Repeats append timeline events to the open generation.
- **One open alert at a time**: use one fixed key on the address. A later email after recovery opens a new generation.
- **New alert per email**: each distinct message opens its own generation.
- **Custom rules**: evaluate up to 20 ordered trigger/resolve rules; the first match decides. Combine 1–20 conditions with all/any. Authenticated sender, subject and plain text support contains, equals, matches and does-not-match. Keys come from a regex capture group or between two literal markers in subject/text. An empty trigger extraction falls back to normalized subject. Empty resolve extraction is a retained no-effect receipt. Trigger rules can set severity, urgency and P1–P5 priority. Lower urgency applies at first admission; later repeats can raise urgency and do not silently lower an existing alert.

Modes 1–3 can also carry resolve rules, evaluated before their regular trigger behavior. Under custom mode, unmatched mail uses the stated fallback: trigger by normalized subject or quarantine with a reason. Matching is case-sensitive except subject-prefix normalization; extracted keys are compared **byte for byte**, without trimming. Keys are scoped to this address and service. A trigger opens a derived generation or appends to the open one; resolve recovers exactly that generation, and resolve without one is retained with no effect. A later failure opens a new generation. Subject/key limits are refused or quarantined rather than truncated into another identity.

A recovered receipt records **stopped by source recovery**, attributed to that email. While paging is OFF, each generation has one labelled, non-automatic obligation; repeats reuse it and recovery records its stopped state. OC-056 inherits actual paging stops and recovered notices before paging ships. A declared incident stays open and still needs its own evidence-backed resolution. OC-038 inherits PagerDuty email settings and Opsgenie email-filter import, naming every unconvertible rule and keeping its original for review. OC-062 inherits managing these modes and rules as code.

The owner activity shows outcome, stable receipt ID, delivery count, mode, rule ID/version, extracted key, action, event and generation. Duplicate Message-ID deliveries on an address retain **one receipt**, increment its delivery count and are explicitly refused without another event. No Message-ID means no retry identity. The original Message-ID is retained only as a digest. **Test draft rules** replays selected saved mail (up to 100 at once) with would-be decisions and no database writes; it neither publishes nor admits events.

### Bounds and retained data

Raw MIME is limited to 512 KiB, depth 12 and 100 MIME parts. Decoded body text/HTML together is limited to 512 KiB. At most 20 attachments, 64 KiB each and 128 KiB total are parsed then discarded; attachment bytes and HTML are never stored or executed. Rules see at most the first 256 KiB of plain text and a 1,000-character subject. Regexes use the existing linear-time RE2 engine with patterns up to 512 characters. Keys are at most 200 characters. An address admits at most 60 new receipts per minute; duplicate deliveries reuse their original receipt. The installation also enforces its existing 1 MB authored-record storage profile, which counts saved mail, email receipts and quarantine but not other intake custody, and its 10,000-receipt capacity; capacity/storage failure refuses delivery rather than confirming success. The 10,000-receipt count is a local limit; it becomes a hosted capacity only under OC-073.

Addresses, versioned rules, saved plain-text samples, receipts and quarantine join the portable archive. Restore removes all address keys, marks every address inactive and replays no email. **Erase saved mail and quarantine** deletes those source copies, revokes the address and fences older native/checkpoint/portable archives; operational alert history and permanent pseudonymous audit remain. Permanent audit commits in the same D1 batch as creation, rotation, revocation, edits and accepted/refused mail, and contains no subject, body, sender, address or key. Retained local tests fake only the provider-delivery edge; a dated, named-SHA real-provider journey is recorded separately in CONTRACT and ACCEPTANCE.
